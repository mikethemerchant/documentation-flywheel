Documentation that maintains itself

Architecture decisions, process docs, system diagrams and an application inventory — as plain text in one Git repo, validated by CI, published automatically.

The dataset is fictional. The method is not.
The problem

How documentation normally dies

  1. Someone writes it — once, in a tool separate from the work
  2. They become the only person who maintains it
  3. They get busy
  4. Six months later nobody trusts it
  5. So nobody reads it
  6. So nobody updates it
Nobody fails at step 1. Everybody fails at step 3.
The problem
The constraint isn't tooling.
It's the attention of the people who know things.

Any process that eventually asks an expert to write something stalls at exactly the moment it becomes useful.

So: build a loop that creates no homework for the expert.
What we built

Three commitments

Text as sourceEvery artifact is a human-readable file. Diffable, reviewable, versioned — and readable by a model.
Data to docsStructured data is transformed into views. Nothing derived is maintained by hand, so nothing derived can drift.
Automation over policyA record with a bad value doesn't get a stern comment in review. It fails the build.

The published site is a projection of the repository — not a second thing to maintain.

What we built

The gate

# inventory/apps/data/meridian-erp.yaml
it_sme: Infrastructure    ← fails the build
it_sme: Priya Raman       ← passes

Every controlled value lives in schema.yaml. Adding a vendor, a person or a team means editing the schema in the same pull request.

An AI assistant cannot invent a person into the owner roster — an unknown value fails validation.
The guarantee doesn't depend on the model behaving well.

What we built

The pipeline — and it caught us

WorkflowTriggerWhat it does
validate.ymlpull request Validates every record, parses every diagram. Writes nothing. A bad value fails here, before merge.
render.ymlpush to main Renders views, generates the landscape diagram, renders D2 → SVG, verifies, commits back, publishes.
The first render committed back a 284-line SVG diff for a diagram nobody had touched — a CSS class name D2 derives per-platform. The first fix was plausible, cheap and wrong. “Nothing derived drifts” is easy to write in a README and takes real work to hold — so DEC-008 stays in the decision log, unedited, marked superseded.

The question you ask each roundWhere the answer lives
Who do we talk to next, and what do we ask them? Register queue, sorted by what each conversation unblocks — not by row count
What's actually stuck, and stuck on what kind of thing? A name, a calendar, or a decision. Three different problems.
Is the loop still turning? Rows arriving vs rows leaving. A register that only grows means conversations aren't happening.
Nobody owns "keeping the docs current." You own the state of this board — and the board tells you what to do next.

Why it matters

Two payoffs

Payoff one

Documentation people trust

Because it's generated from records, reviewed by a human and validated by a build — not because someone promised to keep it current.

Payoff two

Context for the AI

The limit on enterprise AI isn't model capability. It's that the model has no idea what your systems are, who owns them, or why they're like that.

Model memory is per-session, per-machine and lossy. Continuity has to live in files. The repository is the context.
Why it matters

This is a context engineering project

Generic assistant

“Here are general DR best practices for ERP-centric estates…”

Plausible. Generic. Unusable.

Same model, this repo

“The EDI path can't be stopped — partners don't retry, and 40% of order lines arrive that way.”

Specific. Checkable. Sourced to the conversation where somebody said so.

Same model. Different context.

Why it matters

Where the AI is used —
and where it isn't

Used — cheap and genuinely good
  • Reading a messy transcript
  • Drafting structure from prose
  • Finding what contradicts an existing record
  • Turning gaps into briefed questions
Not used — gated
  • Deciding anything
  • Approving
  • Publishing
  • Inventing a fact to fill a field
A human does all four on the right. The schema stops the fourth one even if nobody is paying attention.

Honest scope

What this isn't

Not an EA tool. Not a CMDB. Not a replacement for one.

If you need lifecycle workflows, cost modelling and a hundred stakeholders in a UI — buy something.

This is for the case where you have none of that, need the answers anyway, and would rather own portable text than a subscription.

The demo data is fictional and deliberately imperfect. Unknown owners, undetermined hosting, uncharacterized failure modes.
A demo inventory with no gaps in it teaches the wrong lesson.
